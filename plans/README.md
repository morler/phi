## 目标与边界

最终目标是用 Phi 的 Go 主体和 Glojure 复刻 NodeCode 的可观察行为：模型在持续运行的环境中使用 Clojure 代码扩展自身，定义可被后续调用并跨重启保留；逐步覆盖共享运行实例、cells、上下文、升级与回滚等能力。以用户可观察行为为兼容目标，不要求兼容 Common Lisp 源码、NodeCode 内部 ABI 或数据格式；这三项仅在之后明确需要时单独立项。

Phi 现有工具链必须保持 `ExtensionPre → Gate/Ask → Run → ExtensionPost`；MCP 仍通过 `mcp://` 和 `ls/read/write`；子代理默认只读且不能嵌套。Glojure 的宿主互操作可能绕过工具级检查：一个外层 `eval` 检查或仅隔离进程都不足以证明细粒度文件、命令和网络权限得到执行。未验证的路径一律不得宣称受现有 Gate 保护。

## 关键设计约束

- **权限与取消先行。** NodeCode 的 `eval` 有完整宿主权限，Phi 的现有权限约束不同。阶段 0 必须给出具体决策：哪些操作可按现有 Gate 细分，哪些必须视为具有完整宿主权限的执行；默认拒绝未覆盖路径。受限用户、只读及子代理不能通过 eval 升权。若子进程只负责可终止性，不能将其描述为文件或网络沙箱。
- **状态和终止的权衡。** 单个长生命周期 worker 能保留定义，但杀死 worker 也会失去尚未持久化的状态；恢复必须区分已提交定义、瞬时状态和已发生的外部副作用，不能承诺撤销文件或网络操作。
- **持久化不是重放任意输入。** 不能把所有求值历史在启动时重放。先定义可保留的顶层形式、命名空间、依赖顺序、删除语义和失败处理；对于宏展开、动态定义和副作用，必须有可执行测试或标明尚不支持。
- **Go 与 Clojure 的边界。** 可替换行为必须经过显式桥接或稳定接口；Go 已编译函数不会因为 Clojure 重定义而自动变成可修改。明确哪些能力暂时不可热替换。
- **平台与依赖。** 当前 `go.mod` 使用 `../glojure`，开发期间保留这一事实；在独立检出、CI 和发布前确定包含本地必要修改的可复现依赖，不能未经验证直接删除 replace。
- **兼容与交付。** 保留普通 Phi 模式；实验功能先显式启用，不在只读工具集中注册。通过回归测试和配置迁移后再决定默认行为。可见变更记录在 `CHANGELOG.md` 的 Unreleased。

## 第一条端到端验收路径

在临时工作目录和隔离的 Phi 数据目录中，使用测试模型或确定性工具调用依次完成：启动 → 经正常扩展和权限链调用 `eval` → 定义一个 Clojure 函数 → 下一次调用得到预期值 → 干净退出 → 重启 → 再次调用得到相同值 → 禁用定义后重启并确认不可用。另测拒绝权限、语法错误、执行失败、取消和损坏持久层；确认不会误报成功，也不会让只读子代理获得执行权限。

这条路径是阶段 0–2 的联合验收，不是仅凭 REPL 或单进程内测试即可完成。多客户端、cells 和运行中升级另有阶段验收。
